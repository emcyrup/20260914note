# 予約管理を単体で動かす（別サーバーでの横展開）

なゆた由来の予約管理を、業務支援システムの一部としてではなく
**予約だけのサービス**として別サーバーに置くための手引きです。

コードは同じリポジトリのままで、環境変数 `RESERVATION_ONLY=True` を立てると
外から見える画面が予約まわりだけになります（フォークやコピーは不要）。

---

## 1. 何が変わるか

| | 通常の構成 | `RESERVATION_ONLY=True` |
|---|---|---|
| URL 定義 | `config/urls.py` | `config/urls_reservation.py` |
| ログイン後の入口 | ホーム（ダッシュボード） | 予約カレンダー |
| サイドバー | 台帳・予定・記録・支援計画・請求・帳票… | 予約カレンダー／顧客／公式LINE／職員・運用管理 |
| 公式LINE | 日誌の配信履歴・送信もあり | Webhook だけ（配信履歴の画面は載せない） |
| 施設設定 | 施設設定の画面 | 予約の設定（カレンダー画面の下）と、公式LINE画面のつなぎ先 |
| 施設設定の「使う機能 → 予約管理」 | オンのときだけ予約が見える | 見ない（このサーバーは予約専用） |

記録・請求・支援計画などの URL は **載せません**（`/records/` などは 404）。
同じデータベースを共有することは想定していません。別サーバー・別データベースで動かします。

---

## 2. 立ち上げ手順

```bash
git clone <このリポジトリ>
cd 20260914note
python -m venv venv && ./venv/bin/pip install -r requirements.txt

# .env（サーバーにだけ置く。リポジトリには入れない）
cat > .env <<'ENV'
SECRET_KEY=<十分に長いランダム文字列>
DEBUG=False
ALLOWED_HOSTS=yoyaku.example.jp
CSRF_TRUSTED_ORIGINS=https://yoyaku.example.jp
DB_NAME=...            # PostgreSQL を使うとき
RESERVATION_ONLY=True
RESERVATION_SITE_URL=https://yoyaku.example.jp
ENV

./venv/bin/python manage.py migrate
./venv/bin/python manage.py collectstatic --noinput
./venv/bin/python manage.py createsuperuser     # 最初の管理者
./venv/bin/gunicorn config.wsgi:application --bind 127.0.0.1:8029
```

`RESERVATION_SITE_URL` は、LINE の返信に載せる顧客ページのアドレスの入口です。
空のままでも動きます（返信にリンクが付かないだけ）。

前段の nginx / Caddy では `/media/` を直接配信しないでください
（アップロードした画像は、ログイン中の職員の事業所のものだけを返す作りです）。

### 事業所と職員をつくる

1. `/admin/` に superuser で入り、施設（Facility）を1つ作る
2. 同じく職員（StaffAccount）を作る。`役割 = 管理者`、`施設` に上の施設を選ぶ
3. 以後は `/accounts/staff/` の招待リンクから職員が自分で登録できる

## 3. 予約のしくみ（通常構成と同じ）

- 枠は **1日あたりの人数**（時間帯では分けない）。休業曜日と臨時休業日は枠0
- 満枠のときはキャンセル待ち。取り消しが出たら **申し込み順に** 繰り上げ
- 同じ日・同じ利用者の予約は1件まで
- 予約の入口は4つ：職員の画面 / 顧客ページ / 公式LINE / スタッフのLINEグループ

## 4. 予定表を見る・予約する

### 顧客向けのページ（ログインなし）

| ページ | アドレス | 何ができるか |
|---|---|---|
| 空き状況 | `/yoyaku/aki/<公開アドレス>/` | 月ごとの空き（○△×）と、お申し込み。名前は出ない |
| 顧客ごとのページ | `/yoyaku/mypage/<顧客のアドレス>/` | 自分の予約の確認・申し込み・取り消し |

申し込みの入口は2つあり、確定のしかたが違います。

| | 誰が使うか | どうなるか |
|---|---|---|
| 空き状況ページの申し込み | アドレスを知っている方なら誰でも | **その場では予約にならない。** 「予約 → 申し込み」に積まれ、職員が利用者を確かめて「予約にする」を押したときだけ予約になる |
| 顧客ページの申し込み | 顧客台帳にいて、自分のアドレスを受け取った方 | その場で予約（満席ならキャンセル待ち） |

空き状況ページの申し込みは、誰でも送れるぶん次の守りを入れています。

- 自動投稿よけの見えない欄（人には見えない欄に何か入っていたら受け取らない）
- 同じ相手から**1時間に5件**まで
- 受け付ける範囲・休業日・満席（キャンセル待ちを受けない設定のとき）は、その場で断る
- 設定「お子さまの名前が在籍者1人に決まるときは、その場で予約にする」を入れたときだけ、
  名前がちょうど1人に一致する場合に限り自動で予約にする（既定 off）
- 申し込みには連絡先が残ります。処理ずみのものは職員が削除できます

- アドレスそのものが合い言葉です（推測できない長さ）。検索には載せません（`noindex`）
- 空き状況のアドレスは「予約カレンダー → 予約の決まりごと」で確認・作り直しができます
- 顧客ごとのアドレスは「顧客 → 編集」で確認・コピー・作り直しができます

### アドレスを1字でも書き換えたら開けない

アドレスの後半は **署名（チェックサム）** です（`SECRET_KEY` による HMAC-SHA256／`reservations/tokens.py`）。

- 1字でも変える・増やす・減らすと署名が合わず、**データベースを引く前に 404** になります。
  打ち間違いでたまたま他の方のページが開くことはありません
- 署名は **ページの種類ごとに違う鍵**（salt）で作ります。空き状況のアドレスを顧客ページの
  URL に貼っても、その逆でも開けません。道の名前も `aki` と `mypage` で分けてあり、
  1字違いの関係にはなっていません
- 開けないアドレスが続いた相手は記録に残します（`logger.warning`）。
  正しいアドレスはいつでも開けるので、打ち間違いが続いても本人は締め出されません
- 照合は定数時間（Django の `Signer`）で、当たっているかどうかを応答時間から測れません

> ⚠️ **`SECRET_KEY` を変えると、配ったアドレスはすべて開けなくなります。**
> 古い鍵を `SECRET_KEY_FALLBACKS` に残すか、下のコマンドで作り直して配り直してください
> （まだ誰にも配っていなければ、そのまま作り直すだけで済みます）。

```bash
# 署名が合わなくなったものだけ作り直す（SECRET_KEY を変えたあと）
python manage.py reissue_reservation_tokens --only-broken

# 事業所を指定して全部作り直す（アドレスが漏れたおそれがあるとき）
python manage.py reissue_reservation_tokens --facility 3
```
- 受け付ける範囲（何日先から・何日先まで）と、そもそも申し込みを受けるかは設定で変えられます
- 顧客ページからの操作（申し込み・取り消し）は、1つのアドレスにつき1時間30回までです

### 職員の画面

予約カレンダー → 日を選ぶと、その日の予約の一覧です。

- **追加**：利用者を選んで追加（満枠ならキャンセル待ち）
- **変更**：日にちと備考を変える。もとの日はキャンセル待ちを繰り上げ、
  変更のお知らせを送信待ちに入れる
- **取り消す**：取消として残し、キャンセル待ちを繰り上げ、顧客へ取消のお知らせ
- **削除する**：間違って入れた予約を記録ごと消す（顧客へのお知らせは送らない）

## 5. LINE から予約する

### 「予約」と送られたとき

日にちの書かれていないお問い合わせ（「予約」「空いてますか」など）には、
**顧客向け予定表のアドレスを自動でお返しします**（設定は不要）。

| 送り主 | お返しするページ |
|---|---|
| 顧客台帳にいる方 | その方専用のページ（確認・申し込み・取り消し） |
| はじめての方 | 空き状況のページ（公開しているときだけ） |

日にちが書かれた文は、あわせて受信箱にも積みます（職員が確かめられるように）。
アドレスの入口は `RESERVATION_SITE_URL`、無ければ Webhook を受けたホストです。

### 顧客（公式LINEへのメッセージ）

「予約の設定 → 公式LINEから直接受ける → 顧客からの申し込みをその場で反映する」を
オンにすると、次の条件がそろったときだけ、その場で予約になります。

- 送り主が **顧客台帳にいる**（LINEのユーザーIDが登録されている）
- 日にちが読み取れる（`9/20`・`2026-09-20`・`明日`・`今日`。1通に5日まで）
- 利用者が決まる（文中の名前、または担当する利用者が1人だけ）
- 受け付ける範囲の日である

反映できたときは、その場で LINE に返事をします（送信待ちには積みません）。
読み取れない文は、これまでどおり **受信箱** に積み、職員が確かめてから反映します。

例：

```
9/20 予約おねがいします
9/20 9/21 おねがいします
9/20 キャンセルします
空いてますか？
```

### 職員（スタッフのLINEグループ）

公式アカウントをグループに入れ、そのグループで1度投稿すると
「公式LINE」の画面に出ます。そこで **お知らせ先のグループ** に登録すると、
以後そのグループの投稿がそのまま予約になります（設定でオフにできます）。

```
9/20 青木はると 予約
9/20 青木はると キャンセル
9/20 空き
```

- 名前と日にちが読み取れない投稿は、受信箱に積むだけです（自動では反映しません）
- お知らせ先に登録していないグループの投稿は、いつでも受信箱に積むだけです
- 職員のグループからの予約は、顧客ページの「受け付ける範囲」を見ません（当日ぶんも入れられます）

## 6. 通知

予約の受付・キャンセル待ち・繰り上げ・取消・変更・前日のお知らせ・空き枠は、
**送信待ち** に積み、職員が「まとめて送る」を押したときに送ります
（LINE 未連携の方のぶんは「コピーして送る」として残ります）。
LINE の投稿からその場で反映したぶんは、返信でお伝えするので送信待ちには積みません。

## 7. 通常構成との行き来

同じコードなので、`RESERVATION_ONLY` を外せば業務支援システムの一部として動きます
（そのときは施設設定の「使う機能 → 予約管理」で表示を切り替えます）。
データは別サーバー・別データベースのままなので、移すときは CSV か DB の移行で行ってください。
